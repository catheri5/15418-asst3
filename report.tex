\section{Implementation Status}

We first implemented a sequential correctness baseline before adding OpenMP
parallelism.  The starter code's compressed route representation was replaced
with a keypoint representation: each wire stores up to five points, corresponding
to the start point, up to three bends, and the end point.  This matches the
assignment checker format and makes route construction and validation easier to
reason about.

During initialization, each input wire is assigned a simple legal route.  If the
endpoints share a row or column, the initial route is straight.  Otherwise, the
initial route is a horizontal-first one-bend path.  The occupancy matrix is then
constructed by adding each initial wire route.

The current baseline rerouting algorithm visits every wire for each iteration.
For a wire being reconsidered, the current route is first removed from the
occupancy matrix.  The program then generates every legal route with at most
three bends, scores each route using the sum of squared occupancy values that
would result from adding the wire back, and chooses the lowest-cost route.  Ties
are broken by preserving the existing route.  The selected route is then added
back into the occupancy matrix.

\section{Route Generation and Cost Calculation}

For non-collinear endpoints, route generation currently includes horizontal-first
and vertical-first routes with at most two bends, plus exactly three-bend routes
through each strictly interior point in the endpoint bounding box.  Choosing
strictly interior points for the three-bend case prevents those routes from
collapsing into duplicate one- or two-bend routes.  Some at-most-two-bend routes
do collapse to one-bend routes; consecutive duplicate keypoints are removed when
constructing the wire.

When scoring a candidate route, the current wire has already been factored out
of the occupancy matrix.  Therefore each occupied cell on the candidate route is
scored using $(occupancy[y][x] + 1)^2$.  This computes the route's relevant
contribution if the current wire were added back along that path.

\section{Within-Wires Parallelism}

The first OpenMP implementation target is the within-wires strategy.  For a
single wire, all candidate routes can be scored independently while reading the
same occupancy matrix.  We plan to keep the outer loop over wires sequential at
first, generate the candidate routes for the current wire, and parallelize the
route-scoring loop when the number of routes is large enough to amortize OpenMP
overhead.

Our current within-wires implementation uses per-thread local best routes during
the parallel route-scoring loop.  Each worker scores a subset of candidate
routes and records its best local route and cost.  After the parallel loop, the
main thread reduces these per-thread results to choose the route for the current
wire.  This avoids locking inside the route-scoring loop.

We are comparing static and dynamic scheduling policies.  Since different wires
can have very different numbers of candidate routes, we also test a threshold
below which route scoring remains sequential.  The goal on the GHC machines is
to expose enough route-scoring work to keep up to 8 threads busy.  For the later
PSC experiments, the same design will need to expose enough work to scale toward
128 threads.

\subsection{Within-Wires Design Discussion}

Our first within-wires design kept the outer loop over wires sequential and
parallelized only the exhaustive route search for the current wire.  This choice
matches the structure of the algorithm: after the current wire is removed from
the occupancy matrix, all candidate routes for that wire can be evaluated
independently while only reading the shared occupancy matrix.  We initially used
a simple sequential baseline for both modes, then added OpenMP parallelism inside
the route-scoring loop.

Inside the parallel route-scoring loop, each thread maintains a private best
route and cost.  After the OpenMP loop finishes, the main thread reduces these
per-thread bests to select the final route for the wire.  This design avoids
synchronization in the inner scoring loop: threads read the same route list and
occupancy matrix, but they do not update shared best-route state while scoring.
Conceptually, this is similar to using a reduction for an accumulated sum: each
thread accumulates its own partial result independently, and the partial results
are combined only once at the end.  In our case the reduction operator is
``choose the lower-cost route'' rather than addition.  This exposes more of the
route-scoring loop to parallel execution than having every candidate route
compare against and update a single shared current best.
The only shared update for the wire is the sequential removal of the old route
before scoring and insertion of the chosen route afterward.

We considered static and dynamic scheduling, thresholding the number of routes
required before entering the parallel path, and changing the OpenMP chunk size.
The preliminary tuning results showed that these knobs had only modest impact.
Static scheduling was slightly faster than dynamic in the corrected comparison,
a threshold multiplier of 4 was the best of the tested values, and chunk size did
not materially change performance.  Based on these results, we chose static
scheduling with a threshold multiplier of 4 and chunk size 8 as a stable
configuration for further within-wires measurements.

We do not expect perfect speedup from this approach.  The outer loop over wires
remains sequential, route generation and final best-route reduction are also
sequential for each wire, and a new OpenMP parallel region is entered for many
wire searches.  In addition, candidate scoring performs many reads from the
occupancy matrix, so cache behavior and memory bandwidth can limit scaling.
Some wires also expose fewer candidate routes than others, so the amount of
available route-level parallelism varies over the execution.

At high thread counts, we expect within-wires scaling to eventually flatten or
possibly drop off.  The number of candidate routes for a single wire limits the
maximum useful parallelism for that wire, while parallel-region overhead and
memory-system pressure increase with more threads.  The GHC experiments focus on
1, 2, 4, and 8 threads; higher-thread behavior will be evaluated more directly
in the PSC scaling experiments.

\section{Planned Across-Wires Parallelism}

The across-wires strategy is more complicated because different threads make
route decisions that update the shared occupancy matrix.  Our initial plan is to
follow the assignment's batch model: a worker obtains a batch of wires, processes
the wires in that batch sequentially, and then updates the occupancy matrix for
the chosen routes.  We will vary the batch size to study the tradeoff between
synchronization overhead, staleness, load balance, and final routing quality.

Potential synchronization strategies include a single global lock, row-level
locks, and tile-level locks.  We expect the simplest correct version to use
coarser synchronization first, then refine the locking granularity only if
measurements show that update contention is a bottleneck.

\section{Optimization Hypotheses}

The main performance themes we plan to evaluate are workload balance,
scheduling overhead, locality, and contention.  Within-wires parallelism exposes
candidate routes as independent tasks; this should work best for wires with large
bounding boxes and many possible routes.  Across-wires parallelism exposes wires
or batches of wires as tasks; this may require dynamic scheduling or
longest-task-first ordering to avoid stragglers.

We will also consider locality-aware across-wires batching as a later experiment.
For example, wires could be grouped by bounding-box midpoint or quadrant so that
threads tend to work on nearby occupancy cells.  This may improve cache locality,
but it may also increase contention because nearby wires are more likely to
overlap.  We will only pursue this direction if cache miss or synchronization
measurements suggest that the extra work is justified.

\section{Experimental Plan}

For the GHC experiments, we will collect results for 1, 2, 4, and 8 threads for
both within-wires and across-wires implementations.  We will report total time,
computation time, speedup, cache misses, maximum occupancy, and total routing
cost.  After the GHC implementation is stable, we will run the required PSC
scaling experiments for 1, 2, 4, 8, 16, 32, 64, and 128 threads.
